## Why

A meeting holds decisions and asks that change a repository's work.
Finding the meetings is arithmetic: which services, since when, how
long, under what id. Reading them is judgment. eddy does the arithmetic
and leaves the judgment to a session, so no model runs to list a day's
meetings, and a meeting keeps one key however often it is listed.

<Flow>
  <Step kind="list" title="List">
    A part per service lists the meetings recorded there since its
    cursor and fetches each transcript. No model runs.
  </Step>
  <Step kind="key" title="Key">
    eddy keys each meeting by its service and the meeting's own id,
    `meeting/wispr/7f3c2a`. The same meeting gets the same key from
    every host and every run.
  </Step>
  <Step kind="keep" title="Keep">
    It writes the transcript as the service served it, plus a plain copy
    with one line per turn, and skips a meeting too short to hold
    anything.
  </Step>
  <Step kind="read" title="Read later">
    A session reads the transcript later and writes its signals through
    millpond. eddy never reads a meeting.
  </Step>
</Flow>

## Services

Each part keys a meeting as `meeting/<part>/<meeting id>`.

| Part | Source | When |
|---|---|---|
| `wispr` | Wispr Flow's MCP endpoint, as an MCP client with its own sign-in | first |
| `webex` | Webex's transcripts API | when a partition records on Webex |
| `teams` | Microsoft Graph's meeting transcripts | when a tenant's administrator consents |

Any other service joins as a plugin of its own that passes the meeting
checks, and a generic MCP part and millpond's folder drop take the
rest.
